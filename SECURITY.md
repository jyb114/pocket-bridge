# Security

Pocket Bridge is an unofficial, self-hosted gateway for accessing DeepSeek Harness (DSH) or Codex running on your own computer from a phone browser. It is not a hosted service or a multi-user security boundary. The computer, its accounts, and the separately installed DSH or Codex remain under your control.

## Reporting a vulnerability

Please do not post exploit details or secrets in a public issue. Once this repository is public and GitHub Private vulnerability reporting has been enabled, use **Security → Report a vulnerability**. GitHub does not offer that feature for a private repository; the maintainer must enable and verify it immediately after publication. If the button is not available, you may open a *non-sensitive* issue asking for a private reporting channel, without including vulnerability details.

Include the Pocket Bridge version, operating system, affected component, impact, and minimal reproduction steps. Remove access keys, full connection URLs, cookies, account data, and personal content from any report. This is a personal project; no response time or service-level agreement is promised.

## What the current protection does and does not cover

The full connection URL is a credential. Its path contains an access key, and its `#` fragment contains a separate secret used for client proof and protected content channels. A six-digit pairing code alone does **not** authorize access to protected conversations. Keep the complete URL private and rotate keys if it may have leaked.

For a TryCloudflare connection, Cloudflare terminates HTTPS. It can see URL paths, cookies, traffic timing and size, and any request or response that Pocket Bridge has not separately encrypted. The fragment is not normally sent in the HTTP request, but that fact does **not** make it safe from an actively malicious relay: a changed first page or a redirect can disclose it. The first page and its scripts are not end-to-end authenticated. Code-integrity checks cannot establish trust in the very first page delivered by that relay.

Application-layer encryption depends on the phone view and route. It does not authenticate the first page delivered by the tunnel:

| Channel | Current boundary |
|---|---|
| Bridge-owned DSH phone view | Its protected project, conversation, prompt, live event, approval, directory, upload and download routes require encrypted request and response bodies over the tunnel. The computer's DSH still performs the work. URLs, cookies, timing, sizes and initial page/scripts remain visible. |
| Codex phone view | Covered real-time and content routes require application-layer encryption over the tunnel. The updated file browser sends local file paths inside encrypted POST bodies and receives encrypted bytes. This does not certify every possible route or the first page. |
| Experimental native Codex desktop relay | Its content endpoint requires the existing gateway authentication and device proof plus an encrypted request and reply. It operates the verified official desktop conversation after checking its UUID and project directory. Sending supports plain text; native approvals, questions and attachments are not forwarded by this route. |
| Experimental native Your dot text | Connect, Refresh and Send require gateway authentication, device proof and encrypted content. The reader verifies the durable conversation identity and extracts only recent loaded message rows. Sending supports plain text and checks an exact fresh row in that conversation. A 14-check actual local Send flow and a 19-check unknown-receipt recovery used real encryption and the production private-storage provider with isolated device proof; the latter retained its accepted receipt after normal close/reopen. A subsequent public browser Send and Connect/Refresh re-reads displayed the same Dot's unique model reply through production authentication, device proof and encrypted content, without another Send. Physical-phone/5G and other workflow acceptance remain pending. Neither chat delivery nor encrypted transport establishes local computer execution. |
| Original DSH view (`view=classic`) | Covered WebSocket events and outbound prompt/upload bodies are encrypted; the gateway now rejects unencrypted remote prompt/upload writes. Other DSH HTTP API and history **responses can still be plaintext** to the TLS-terminating relay. Use the bridge-owned phone view for the stronger content boundary. |

The gateway also requires proof of the fragment secret before serving protected HTTP or WebSocket content to a remote device. This reduces what someone can do with the access key from the URL path alone; it does **not** protect against a relay that can replace the page or redirect the browser. A successful device proof is temporarily retained by device ID, including across gateway restarts. A relay that obtains an already-proven device cookie may reuse that device's access window; do not treat proof as protection against a malicious relay. Protected requests reject missing or invalid encryption instead of silently forwarding plaintext. Testing is not a guarantee of complete coverage or security.

Codex history compression stays inside the existing authenticated AES channel; gzip is not encryption. Complete page output and cursors are preserved, and every poll still queries the app-server. Fresh HMAC revisions belong to one connection; nonce, exact page scope, encoding, UTF-8 and decoded size are checked before cache use. The phone retains at most four serialized pages totalling 8 MiB of decoded content, and reparses them before returning data. The optimized result limit is 8 MiB. Every encrypted WebSocket frame, including other RPCs and deliberate full-page retries, has a 16 MiB limit. Oversized pages fail explicitly rather than returning a truncated success. TCP splitting/coalescing is supported; fragmented application frames fail closed before the AES transform can normalize their FIN flag. Identity content on browsers without gzip and the correlated method-not-found fallback retain encryption and allow only the original history read, never replaying a write. Compression does not conceal traffic sizes/timing or repair the first-page trust boundary.

Rotating only the `#` fragment secret changes the content-encryption secret; it does **not** revoke the access-key path, existing device cookies, or an already-retained device proof. If the complete link, a cookie, or a device may be compromised, revoke that device and rotate the **access key** with session revocation. An older cached Codex page may send a file path in a GET URL before the updated gateway rejects it over a tunnel; reopen the updated phone page to use the encrypted POST route. Classic DSH API responses remain outside the content-encryption boundary described above.

On a local network, the HTTP entry point is plaintext; the optional local HTTPS entry point uses a local certificate that your device must validate appropriately. A direct Internet HTTP entry point is also plaintext. See [README.md](README.md) for the supported connection modes and their trade-offs.

This preview starts only Cloudflare tunnels; the old ngrok fallback is disabled. The gateway rejects local-console access and requires the remote encryption boundary when an incoming request has a public Host or forwarding headers, even if the socket peer is loopback. Arbitrary reverse proxies are not supported. If a proxy rewrites Host to a local address and removes every forwarding header, the gateway cannot distinguish its remote requests from requests made on the computer itself. Do not publish the gateway through such a proxy.

The direct-loopback device-proof exemption also rejects relay and forwarding indicators before examining the local socket and Host. A local Host alone cannot turn a forwarded request into a local exemption. Nine isolated loopback HTTP checks passed for these refusals and the ordinary direct-local path; they do not establish every proxy deployment's security.

The gateway binds its real IPv4 loopback listener before advertising the port. On Windows, LAN and optional IPv6 listeners share the gateway's handlers, and health at the exact advertised IPv4 origin must match the installation, PID and boot. Actual socket tests reproduced a conflicting local listener diverting the old tunnel and checked occupied-port recovery. Tunnel probes accept only the exact gateway HTTP 204 response, and stop reading after the response headers; foreign pages, redirects and errors are unhealthy. Fourteen isolated HTTP/TCP cases checked this response boundary, absolute header deadline and socket cleanup. A real gateway/tunnel migration passed matching local health and a public probe. This helps prevent accidental upstream confusion; it is not a security boundary against a malicious local program or a compromised computer, and a public probe does not establish protected-content acceptance.

Controlled Bridge stop and restart refuse new desktop operations before draining owned child processes and the full receipt tail. An unconfirmed drain or failed initialization blocks the controlled exit; it does not authorize force termination or removal of ownership evidence. Local stop/reload admission is pinned to the verified installation and gateway boot, with PID binding for reload. The console uses a new process boot identifier rather than the persistent installation identifier to confirm restart. A source-install migration verified a new live gateway boot, and a later actual port recovery verified matching local health and a public probe. General tray operation and every production shutdown state remain unaccepted. Abrupt crashes, external termination and power loss are separate failure boundaries: retained evidence is not a promise of graceful clipboard restoration or automatic recovery.

Managed daemon startup uses a per-install operation lease. Stop intent fences delayed gateway and tunnel creation, and the tray waits for that lease before confirming completion or cleaning up newly observed owned tunnels. Incomplete, replaced or uncertain lease records stay blocked; elapsed age or a dead PID alone does not permit takeover. This protects the tested managed stop path and does not prevent an external process or user from separately starting software.

An additional real Windows countercase changed only the ACL of an owned Dot store fixture, leaving its encrypted file bytes unchanged. The cached provider detected the change and refused access; restoring the original ACL did not silently reactivate that failed store. This is evidence for the tested Windows filesystem and provider path, not a guarantee for every filesystem or compromised same-user process. Failed providers discard cached secret material without using that failure to clear unresolved ownership or delivery evidence.

## Outside the security boundary

Codex conversation control uses the app-server's exclusive writer mechanism. A writer conflict does not identify the owning Windows process. Pocket Bridge therefore refuses desktop termination when that owner cannot be verified and never treats an unrelated running Codex process as authorization to stop it. Explicit phone handback unsubscribes the idle conversation and pauses that phone's live connection until a deliberate reconnect. It reports this separately from verified writer availability. Codex 0.159.0 retained the idle writer for approximately 60 seconds in the earlier actual test; other releases may behave differently. The native desktop relay instead uses the existing writer through the official app; it does not take a phone writer or bypass the lock.

Native Codex and Dot actions share a fail-fast desktop-action lease and per-user Windows mutex. These guards prevent overlapping Bridge helpers, not simultaneous human input or unrelated desktop automation. Leave the computer free during a native phone operation. Existing drafts, unresolved identity and uncertain receipts stop or limit submission; an uncertain result must not trigger automatic resend. The helpers briefly use the clipboard and attempt to restore it on normal completion. Forced termination may prevent cleanup, so clipboard restoration is not guaranteed after a timeout.

The Codex outgoing-source check uses the complete attachment-free blank-composer proof, including the exact supported compact and expanded active layouts. The observed compact dictation `contents` wrapper alone may report offscreen while its exact button/icon remain visible and enabled; this exception does not propagate to children or other controls. A missing Chromium text selection is not permission to ignore a draft: real operation demonstrated the full blank proof on a running source, followed by a separate genuine-draft refusal on the target. Later native Sends received confirmed receipts and unique replies. One public browser Send to a noncurrent conversation also passed production authentication, device proof and encrypted HTTP with its unique reply visible; an earlier current-conversation public operation remains unknown and was not resent or reset. The product does not automatically clear user drafts or weaken conversation UUID, canonical project, process-lifetime, window or Send-control checks. The complete source/outgoing suite passed 117 isolated regressions; these are separate from actual send acceptance.

Native process verification now holds a query/synchronize-only handle before the exact fresh CIM birth/path comparison. Later checks verify the same continuously live object, full 100 ns creation time, PID and normalized executable; failure never permits reopening or trusting a cached PID. Owned-process and isolated identity checks passed 48 cases. A cross-project attempt then failed before Send when composer focus had not settled, preserving its draft. Readiness now waits at most 1.2 seconds after one SetFocus, rechecking the same unique composer and bound process/window/foreground without sending input. Foreign focus, changed identity or composer ambiguity abort, and the original strict final focus gate remains; 52 synthetic checks passed. An installed public different-project Send subsequently passed with its unique reply visible and unchanged phone draft cleared, while desktop Codex stayed open with no writer takeover. This does not certify every state or a physical phone, or change the earlier unknown send's status.

Current-Dot classification with a dismissed profile does not rely on the window mode or placeholder text alone. Only the exact supported blank Dot composer and complete control tree, with repeated bound root, mode, editor, raw pane and viewport identities, may open the unique metadata profile. A draft, changed context or ambiguous control refuses that path; durable conversation identity is still copied and checked afterward. The 32 complete synthetic UIA regressions exercise the guard without operating a real desktop.

The separate post-navigation Dot readiness wait occurs only after one already-verified sidebar invocation. For at most three seconds it samples metadata with fresh process-lifetime, executable, main-window and foreground checks. Only zero-control transitions can wait; duplicate candidates fail immediately. It adds no input action, second navigation or Send and does not replace the outgoing-draft, clipboard, rendered-scope or durable-identity safeguards. Fifty-one isolated contract checks passed. The subsequent public Connect/Refresh re-reads displayed the same Dot's unique reply to its previously accepted Send; that bounded production case does not certify every native state or physical phone.

Dot Check receipt obtains the original unresolved operation and full baseline only from the private encrypted journal; the phone cannot supply proof fields, replace a baseline or authorize another Send. The native observer reattests its helper before both read acknowledgements and binds the original desktop process lifetime, window and version. A dismissed profile popover may reopen through its unique observed metadata control only after the original rendered viewport and message-list identities match, with fresh control and scope checks around the toggle. It does not paste, change drafts, invoke Send or Stop, or navigate between conversations. It briefly focuses the composer to copy its durable conversation identity while preserving the clipboard. Acceptance requires the entire original row prefix and exactly one appended user row with the original text hash. Another user action, changed context, incomplete rows or an oversized scope leaves delivery unknown. Baselines retain at most 128 complete loaded rows, with at most five appended rows; no old prefix is discarded. A failed check reports a separate retry hint without rewriting the original receipt. A 19-check actual local run deliberately lost the terminal result after one native Send and recovered the unknown receipt through one read-only native observation without replay. Normal close and real DPAPI/ACL store reopening preserved that accepted receipt. This local recovery is separate from the accepted public Send/Connect/Refresh case and does not establish production or physical-phone unknown-receipt recovery.

The experimental Dot private store uses an independent random key, protected with Windows current-user DPAPI, for its AES-256-GCM journal. Its private paths enforce a current-user ACL. A real isolated Windows provider test passed protection, ACL validation, opening and reopening. The actual unknown-receipt recovery also closed and reopened the real protected store while retaining its accepted receipt, using isolated device proof. These results do not certify the full production authentication or deployment workflow. Status reads do not provision this store or start native actions. Codex relay journals and saved-message queues may still contain plaintext submitted text on the computer. Unsent Codex phone drafts are retained as plaintext in the current tab's origin-scoped `sessionStorage` and are not written to `localStorage`; this restores bounded, per-conversation text on a same-tab reload without sending it. Up to 16 drafts, 32,768 UTF-16 code units per draft, and 131,072 serialized code units in total are retained; larger drafts stay only in page memory. Browser session restoration may retain that storage, and storage denial or clearing can prevent recovery. Local keys, browser storage, the native apps' own history and other target runtime data are separate boundaries. Do not assume all local content is encrypted at rest, or that current-user DPAPI protects against malicious code running as that same user or a compromised computer.

In preview.7, Dot retains bounded drafts and unresolved request text as plaintext in the same tab's `sessionStorage`. Records are separated by gateway origin, a domain-separated fingerprint of the phone connection key, and the verified durable Dot identity. The connection key itself is not written into those records. Reload recovery requires an encrypted snapshot of the same Dot; it does not reconnect or send automatically. Closing a tab, denied storage or browser session cleanup can prevent recovery. This protects against accidental cross-connection draft reuse, not malicious same-origin scripts or a compromised browser.

Dot's private cloud interfaces and desktop authentication cookies are not proxied by either the official-access guide or native reader. The separate MCP inbox prototype has a different boundary: OpenAI receives plugin message text to process it, and Cloudflare can read that MCP traffic when it terminates TLS. HTTPS on that route is not end-to-end encryption through the cloud plugin. This prototype has not passed an actual Dot subscription/reply workflow.

Codex file reads are confined to registered project roots, Bridge-owned uploads, and the known generated-output roots. A parent folder is not granted by a child project. Credential files, private configuration directories, links escaping the allowed root, multiple hard links, and Windows alternate data streams are rejected. SVG, HTML, XML, and script documents are served as safe text/attachments rather than active image documents; encrypted file metadata retains that safe type after decryption. Ordinary raster image preview remains supported. These file-read limits do not constrain what a separately authorized Codex tool can access through the target's own permissions.

Legacy DSH interaction requests are bound to the observed runtime, process, port, and conversation. Responses must still match a pending request and an allowed choice. Legacy image receipts are short lived, bound to the project and runtime, and consumed through an explicit send; generic file uploads are not supported by that old protocol adapter. The protected legacy helper routes require encrypted bodies over a remote connection. Their automated checks and successful read-only pending-interface checks do not establish a completed model-triggered approval on an old npm release.

- A compromised computer or phone, or anyone who can read local keys or browser storage.
- An active TLS-terminating relay that changes the first page or redirects the browser.
- Traffic metadata, denial of service, and reliable delivery of temporary tunnel or notifications.
- Third-party services used by optional notifications or balance checks; enabling them may disclose notification content or account data to those services.
- Perfect replay prevention across gateway restarts. Replay defenses are best-effort and are not a substitute for a persistent, end-to-end protocol sequence.

## Safer use

- Prefer the local encrypted entry point when the phone and computer are on the same trusted network. A self-managed transport that keeps TLS termination on your computer avoids the third-party HTTP relay, but requires careful certificate and network configuration.
- Use only the complete connection URL copied from the computer console; do not publish or screenshot it. A changed tunnel address or rotated key requires updating the phone bookmark or home-screen shortcut.
- Keep the host computer and DSH/Codex updated. Revoke unused devices and rotate keys after suspected disclosure.
- Run `node scripts/secret-scan.js --strict` before publishing source. This check does not prove that the application is secure.
