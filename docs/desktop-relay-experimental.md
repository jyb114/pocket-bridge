# Experimental desktop relay — work in progress

The scoped Codex desktop relay described below was included in the published `v1.0.0-preview.6` prerelease. It passed the specific local cases recorded here; installing a release does not automatically update an already-running Bridge. Preview.7 adds native Dot text sending and actual unknown-receipt recovery, corrected Codex source-layout proofs, lossless encrypted history transport and accepted public Codex and Dot text cases. The source was installed on D: and a fresh live gateway boot was verified. Acceptance of every desktop state, complete production workflows and physical phones remains incomplete.

The current local verification baseline is the official ChatGPT desktop application **26.928.31416** (Windows package **26.928.3736.0**, registered as `OpenAI.Codex`) and **Codex CLI 0.159.2**. The product version comes from the installed `owl-app.ini`; the Windows package uses a separate version number. Earlier native observations used package **26.928.1915.0** and CLI **0.159.0**, and remain evidence for that earlier baseline only. Other desktop or CLI versions are not certified by this work.

The desktop updater now reports **`restart_required`**. Read-only inspection identifies a staged Windows package **26.928.4866.0**, with product version **26.928.40906**. The current application process, registered package and running sandbox service still use the baseline above; the application has not been restarted for this acceptance. A pending update is not a tested running version. Native identity, draft, send and receipt behavior must be checked again after that transition; the baseline-specific final-LF receipt adjustment does not certify the pending build.

The intended route is phone → the bridge on the computer → the verified Codex desktop conversation → its normal composer and Send control. The desktop application remains the conversation's writer. This route does not require taking over its conversation lock, deleting lock files, or closing Codex. It uses normal foreground desktop interaction, so users must leave the computer unused while using this phone mode. Concurrent keyboard, mouse, clipboard, or conversation navigation can interrupt the operation.

The helper verifies the installed package, publisher, executable and window process. When a launch is needed, Windows application activation (`ActivateApplication`) targets the exact main application AUMID, `OpenAI.Codex_2p2nqsd0c76g0!App`. Conversation navigation uses the Windows Runtime launcher with `TargetApplicationPackageFamilyName` set to the verified package family. It does not rely on a guessed command line or the computer's default protocol handler.

The intended send contract is deliberately bounded:

- Send only after verifying the exact conversation UUID and canonical project directory. If either identity is unavailable or mismatched, stop before submitting.
- Preserve an existing desktop draft. Do not replace it with the phone message. If the composer changes during preparation, stop and let the user inspect the draft.
- Accept plain text only in this experimental mode. Attachments, file transfer and rich composer features are not supported by this route.
- Confirm delivery using a new, uniquely attributable message or queued-item receipt from the same conversation. A receipt confirms submission, not model execution or task completion.
- When a task is busy, the desktop application may queue the new message. **Queued does not mean immediately executing.** This route does not promise to interrupt the running task or change its scheduling.
- Keep an uncertain result as `unknown`. Do not automatically resend it, switch writers, or release a lock to make it appear successful. The user should check the existing receipt and conversation before trying another send; an uncertain submission may already have reached the desktop.
- Do not claim that desktop-native authorization requests, choices or approval dialogs are mirrored to the phone. That capability has not been implemented or accepted through this desktop route.

The clipboard text proof normalizes CRLF to LF without trimming spaces or real newlines. The additional final LF is accepted only for Windows package `26.928.3736.0` in the verified official package family. Matching still requires a fresh, unique, unclaimed history or queue ID in the correct conversation. Overlapping text variants of a previous queued request are reserved until that request owns its history ID; a later request cannot use a real final newline to claim the earlier delivery. Legacy records keep conservative CRLF reservations, but those reservations do not authorize an unproved normalized-history receipt. Restart reconciliation reads existing history and never repeats the desktop send.

After the outgoing-draft guard changed, controlled reruns passed with another conversation open, another project open, the window minimized and a blank Your dot view. Cross-source drafts were safely refused and preserved. The earlier same-source matrix attempt was interrupted by concurrent desktop automation; the fresh compact-active source correction and successful native Send above are separate evidence, not retroactive acceptance of that matrix case. Nineteen actual read-only phone UI interactions passed, including page reloads that preserve typed multiline drafts and the explicit sending-mode choice. A separate 98-check fixture covered exact draft preservation, denied storage and pending-send races. Immediate execution in an already busy target, interruption recovery, physical phones and other public delivery cases still require their own acceptance. Any unreadable draft or unresolved identity or receipt stops a send; success in the accepted cases is not a guarantee for every desktop state.

The revised Codex history UI was also operated read-only against real app-server history. Older pages retain chronological order and message indexing, late responses cannot replace another conversation, and initial/older-history errors provide Retry. Completed-task polling transferred only small metadata during the measured idle interval, and manual Refresh performed a full read. A deliberately injected initial-read fault followed by Retry retained the draft and real recovered rows. Separate pagination/Retry and polling fixtures passed 26 and 20 cases.

The new encrypted history adapter keeps every page field, cursor and complete command output. It queries the app-server on every poll, then uses lossless gzip or identity content and a fresh connection-scoped HMAC revision for unchanged replies. Cached serialized text is reparsed before returning a page, so callers cannot mutate a later unchanged response. Only a correlated method-not-found permits the original read-only RPC; verification failures do not silently downgrade or retry writes. The decoded optimized result is limited to 8 MiB; an explicit full-page retry bypasses that result limit but still shares the 16 MiB encrypted-frame limit with other RPCs. TCP splitting/coalescing is supported, while fragmented WebSocket application messages are refused before AES normalization. Server and browser transport suites passed 63 and 65 isolated checks. A separate ten-check actual browser experiment deliberately reduced the result cap, then recovered genuine history through an explicit full-page read while retaining its older-page cursor and unsent draft.

An actual 38-check browser run read 450 indexed rows from the real app-server through private AES transport. At modelled 218 KB/s bandwidth, 150 ms latency and 4× CPU throttling, the complete 1,176,356-byte page used 95,698 encrypted bytes and loaded in 2.376 seconds, versus the earlier 9.964-second uncompressed result. An unchanged active page used 326 encrypted bytes instead of a 41,583-byte full result, with zero row replacements or mutations. This was not the production gateway, a physical phone or an actual Cloudflare benchmark; the separate public Send case does not establish these performance figures on a phone network.

The history source was subsequently installed on D: and the live gateway reloaded while retaining its verified tunnel and connection keys. Actual operation of the public Cloudflare page in a 390-by-844 browser loaded latest and older real Codex history without errors. Latest returned to the bottom, and the composer stayed within the visible viewport. These installed public interaction checks are separate from the private modelled timing experiment; no physical-phone, keyboard or public-network latency benchmark is claimed.

Preview.7 adds read-only recovery through **Check receipt** for an original unknown send. The private encrypted journal provides the original request, operation and complete baseline; the public request contains only the bound request and conversation IDs. The helper must match the original desktop process lifetime, window, package version and rendered Dot context. A dismissed profile popover may reopen only through its unique observed metadata control after the original viewport and message-list runtime IDs match, with fresh control and scope checks before and after. It copies the durable identity and reads message rows without pasting, changing drafts, sending, stopping or navigating between conversations. A full unchanged baseline prefix and exactly one newly appended matching user row are required. A later user message or changed context leaves the original result unknown. There is no replay or inferred success from composer clearing; failed checks give a separate actionable hint without rewriting the receipt.

The native baseline limit is 128 complete loaded rows and the after-observation limit is five appended rows, with bounded native-node, stream and timeout limits. The phone reader independently displays at most 40 recent rows. Oversized or incomplete evidence fails closed without tail slicing. Isolated sender/service, encrypted-journal and runtime checks passed at 38, 42 and 28 cases respectively; seven original-window and 13 rendered-scope bindings plus the guarded native read-branch AST also passed. The separate 19-check actual local recovery above accepted one lost terminal result without another Send and retained its receipt after protected-store close/reopen. Expected invalid read proofs do not reset a request or falsely mark the healthy journal unavailable, while continuity and encrypted-commit failures still disable it.

Codex and Dot share a fail-fast desktop-action lease in the Node process, with a matching per-user Windows mutex in their native helpers. A competing operation is refused rather than queued. The lease remains held until the helper exits. Normal completion restores the saved clipboard, but a forced timeout can terminate a blocked helper before its cleanup runs; clipboard restoration is not guaranteed in that case. This mode still requires the user to leave the computer unused during a phone operation.

The native Dot content route requires the gateway's login, device proof and encrypted request boundary, followed by an explicit Connect or Refresh action. Responses carry application-level encryption, including the two actual native reads in the accepted local product test and the later public Connect/Refresh case. The browser rejects an unencrypted reply even if the network forges an "already decrypted" header; only successful authenticated decryption creates that local marker. The initial page and scripts still depend on the transport: an active TLS-terminating relay can replace them, and traffic metadata remains visible. See [Security](../SECURITY.md) for that boundary. The isolated checks and accepted public browser case do not establish physical-phone/5G behavior or every route's security. Local request journals and message queues may store text on the computer, so this work does not claim that all content is encrypted at rest.

The Dot private storage provider separately passed a real isolated Windows test of current-user DPAPI protection, a current-user ACL, opening and reopening. It protects an independent journal key rather than reusing the phone transport key, and the journal uses AES-256-GCM. Steady status reads used no native calls. The actual unknown-receipt recovery also confirmed normal close and reopen with the accepted receipt preserved. These cases used the production provider with isolated device proof; they do not establish full production authentication/content acceptance. Codex relay journals and saved-message queues may still contain plaintext. DPAPI does not protect against malicious code running as the same Windows user or a compromised computer.

Real Dot local execution is also blocked on this Windows 10 Home 19045.6466 installation. The computer appears connected and authorized, but a real `Get-Location` attempt fails during executor setup with `exec-server rejected request (-32603): pin C:\`. Changing the requested directory to D: has not established successful execution. Connection and authorization indicators are not local-read acceptance.

A read-only native experiment reproduced the drive-root failure on both drive roots (C: and D:). `NtCreateFile` with `OBJ_DONT_REPARSE` returned `0xC000050B` for drive-letter Object Manager aliases. Resolving only the drive alias to its actual disk volume, while retaining the no-reparse flag, succeeded on both drives. This matches the [Windows 10 sandbox report](https://github.com/openai/codex/issues/47383#issuecomment-5789617352) and the [official fix](https://github.com/openai/codex/commit/5f371ba30ae4a4bf4527eb0729ab6b36e3a0c123), which uses `QueryDosDeviceW` while keeping filesystem reparse-point checks. The installed packaged sandbox service does not contain the fix's diagnostic strings.

The signed service executable from the [official CLI 0.159.3 release](https://github.com/openai/codex/releases/tag/rust-v0.159.3) was downloaded separately and verified against the release digest and OpenAI signature. It contains the fix, but has not been installed. A standalone executable is not a supported replacement for the packaged service: the production service requires an OS-assigned package identity matching its client. An earlier production MSIX check matched the running **26.928.3736.0** package. The updater now reports a restart-required update, and package **26.928.4866.0** is staged on disk. Its sandbox service has a valid OpenAI signature and differs from the running binary, but read-only inspection still found neither the fix's diagnostic strings nor a `QueryDosDeviceW` import. No patched running desktop service or successful local execution has been verified. No service path, package files, ACLs, authorization state or sandbox settings were changed during this diagnosis.

[Official local-access guidance](https://learn.chatgpt.com/docs/enterprise/cloud-local-access) requires desktop version **26.929 or higher** for Dot local computer access. Both the current and staged product versions are below that documented baseline. Dot local-file access remains **unrepaired and unaccepted**; a supported desktop update and a successful real local-file read are required before claiming it works. Reading visible conversation text, a connected computer or a pending-restart indicator does not establish local execution. Downgrading isolation or fabricating setup/readiness records is not part of this prototype.

The separate Dot inbox prototype's cloud MCP connection has a different trust boundary from the native reader's encrypted phone route. OpenAI must receive message text returned by that plugin's read tool to process it. If the MCP endpoint is exposed through a Cloudflare tunnel, Cloudflare terminates TLS and can technically read the MCP data crossing that boundary. HTTPS is not end-to-end encryption through the MCP plugin. This cloud prototype is not the transport used by the new native Dot reader. Independent home TLS termination or an opaque relay has not been deployed or verified by this work, and must not be presented as tested protection.
